Security

Security and trust

We describe only controls that exist in our code and configuration, and we say plainly what is not done yet. This page is not a certification and does not claim any.

Last updated 30 October 2026

StatusThe signed-in product is built and tested locally but is not connected to this website yet. The controls below describe the backend code. They have not been audited by an independent party.

How sign-in works

LocalBoost uses Google sign-in only. There is no LocalBoost password to guess, reuse or leak. After you sign in, the server issues a random session identifier in a cookie named lb_session that is HttpOnly, Secure and SameSite=Lax, so scripts on the page cannot read it and browsers do not send it on cross-site requests. The server stores only a SHA-256 hash of the identifier, so a copy of the database would not contain usable session values. Sessions expire on a server-enforced time, expired rows are purged every hour, and you can revoke all sessions at once. Sensitive actions such as deleting your account or removing a team member require a recent sign-in.

How we protect Google access

  • Encrypted refresh tokens. The long-lived Google refresh token is encrypted with AES-GCM using a key held as a server secret before it is stored. The ciphertext is excluded from every API response and from your data export.
  • Read-only by default. Reading your profile data is the default. Anything that writes to Google, such as posting a review reply, runs only when the request carries an explicit confirmation; otherwise the server refuses it.
  • Incremental permissions. Search Console is requested separately, read-only, and only when you choose to connect it.
  • Revocation. Disconnecting revokes the token at Google and deletes the stored connection.

Protecting requests

  • Origin checks. State-changing requests must come from an allowed origin, otherwise they are rejected. Combined with SameSite cookies this blocks cross-site request forgery. Mutations are JSON POST requests, never GET.
  • CORS allow-list. Cross-origin access is granted only to the LocalBoost origins, with credentials.
  • Rate limits that fail closed. Public and signed-in routes have per-IP or per-user limits. If the limiter or its database is unavailable, the request is refused rather than allowed through unlimited.
  • Body size limits and request identifiers. Oversized bodies are rejected, and each request gets an identifier to help us trace faults without logging personal content.
  • Bound parameters. Database queries use bound parameters. Spreadsheet exports neutralise cells that start with formula characters, and stored text is returned as data to be escaped by the page.
  • Security headers. The site's header configuration sets X-Content-Type-Options: nosniff, X-Frame-Options: SAMEORIGIN, a strict referrer policy and HTTP Strict Transport Security, applied when the site is deployed.

Website crawler safety

The audit crawler fetches addresses entered by visitors, which is a classic risk. It blocks private, loopback, link-local and other reserved address ranges, including tricks such as decimal or hex address forms, checks every redirect and every probed link again, limits redirects, depth, pages and response size, honours robots.txt, and is rate limited per visitor. It follows the same rules in tests that try to reach internal addresses.

Your data stays yours

  • Tenant isolation. Every query for a signed-in route includes the owner in the condition. Another customer's record returns "not found", not "forbidden", so identifiers cannot be probed. Tests assert that one user cannot read or change another's data.
  • Team roles. Workspaces use owner, admin, manager, analyst and client roles checked on the server, with a log of team changes.
  • Export and deletion. You can download your data and delete your account; see data export and deletion.
  • Short-lived Google content. Cached Google review text and profile details expire on a schedule and are removed when you disconnect.

Payments

Payments are handled by Razorpay. We do not receive or store card numbers. We verify the payment signature on the server before activating a plan, verify webhook signatures with a constant-time comparison, and process each event once. Paid plans are not live yet.

Analytics and privacy

Analytics are first-party, run only after you accept the cookie banner, use a fixed list of events and store no IP address, user agent or free text. Read the cookie policy and privacy FAQ.

Secrets and operations

Secrets are held as server secrets, not in the repository, logs or API responses. The administrator token is compared in constant time and the admin routes answer "not found" when it is not set. Automated tests cover the backend security rules. Hosting is on Cloudflare Pages and Workers with a SQLite-compatible database.

What we have not done

  • No independent penetration test or code audit has been done.
  • We hold no SOC 2, ISO 27001 or similar certification, and we do not claim compliance with any such standard.
  • We have no bug bounty programme.
  • The backend has run against local test databases and mocked services, not against production Google or payment accounts.
  • We have not verified every browser-side control with a formal review. The site uses third-party Google Fonts and, for payment, Razorpay's checkout.

Report a vulnerability

If you believe you have found a security problem, email support@localboost.in with the subject "Security". Please include what you found, the steps to reproduce it and the address affected. We aim to acknowledge within five working days and will tell you what we decide. The details are also in our security.txt file.

Please follow these rules:

  1. Do not access, change or delete data that is not yours, and stop once you have shown the issue.
  2. Do not run denial-of-service tests, mass scans or social engineering against us or our users.
  3. Give us reasonable time to fix the issue before sharing it publicly.

We do not intend to pursue good-faith research that follows these rules. We cannot offer payment for reports.

Other issues

For a normal bug, use the bug report form. Do not send secrets, passwords or personal data in any report.

Frequently asked questions

Is LocalBoost SOC 2 or ISO certified?
No. We hold no such certification and make no such claim. This page lists the controls that exist in our code.
Do you store my Google password?
No. Sign-in is through Google, so we never see your password.
Where do I report a vulnerability?
Email support@localboost.in with the subject Security. See the disclosure rules above.
